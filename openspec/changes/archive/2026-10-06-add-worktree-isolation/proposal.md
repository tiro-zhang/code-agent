## Why

当前子 Agent 虽然拥有独立对话和执行状态，仍与主 Agent 共用工作目录；并发编辑同一仓库时，文件操作可能互相覆盖。需要先提供可独立使用的 Git Worktree 生命周期和目录上下文，让后续团队协作能够在隔离的工作副本上派发任务。

## What Changes

- 使用 Git 原生 Worktree 为声明隔离的子 Agent 创建独立目录与分支，目录位于仓库内的非追踪位置。
- 为目录名称提供有界字符集、长度、路径段和真实路径校验，支持安全嵌套，拒绝路径遍历、祖先链接逃逸和工作树相互嵌套。
- 提供创建、只读快速恢复、进入、退出和删除生命周期；仅完整且归属明确的受管目录可以恢复，同名操作互斥，活动目录不得被另一任务接管。
- 在接受子任务时冻结父工作树的 `HEAD` 提交；实际启动时创建工作副本，明确提示其中不包含父目录未提交的修改。
- 创建后按明确清单复制本地配置、配置 Worktree 专属 Git hooks、软链大型依赖、补齐运行必需的忽略文件，并记录初始化基线。
- 不使用进程级 `chdir`；每个运行持有自己的绝对工作根，内置工具与 Hook 命令显式使用该目录。目录相关缓存以绝对路径标识所属工作区，不因目录切换整体清空。
- 扩展角色 frontmatter，接受 `isolation: worktree`；第一版仅自动隔离声明该字段的 defined 角色，未声明角色与 Fork 的现有行为保持。
- 权限模式和规则继续限制子运行，父当前策略作为上限，明确拒绝优先；不自动把父目录批准改写为子目录批准，缺少批准仍返回非交互错误。
- 退出先等待受控操作收尾并归档父任务所需证据，再决定保留或删除。未提交修改、未推送提交及不确定状态默认保护；后台过期清理依次检查归属、活跃状态和成果。
- 将 Worktree 路径、分支、基线及保留／清理状态纳入子任务结果和必要的持久记录，便于上层继续处理成果。

本变更提供工作副本与默认 cwd 隔离，不增加操作系统文件系统沙箱。共享 MCP 保留服务自己的目录语义；依赖软链仍是共享资源。本章不实现 Worktree 合并策略、跨目录代码同步、多 Agent 并行编排或新的独立 Skill 隔离方式。

## Capabilities

### New Capabilities

- `worktree-isolation`: 受管 Git Worktree 的安全命名、创建与恢复、初始化、运行租约、退出保护、删除及过期清理。

### Modified Capabilities

- `agent-definitions`: 接受并严格校验角色的 `isolation` 声明，冻结本次实际采用的隔离配置。
- `subagent-runtime`: 为隔离 defined 运行绑定独立工作根、冻结创建基线，维护隔离资源生命周期并返回有来源的工作树状态。
- `core-tools`: 将固定工作根明确为当前运行的工作根，内置文件、搜索及命令工具遵守该运行的目录上下文。
- `runtime-context`: 注入子运行实际目录、隔离身份与创建基线，明确父目录未提交修改不在工作副本中，旧路径信息只描述历史。
- `tool-permissions`: 在子实际工作根判定目标和适用权限，保留父策略上限，不跨工作根迁移批准。
- `lifecycle-hooks`: 共享规则和会话 once 状态，子命令动作及目标路径使用子工作根，目录释放前完成关联动作收尾。
- `project-instructions`: 隔离子运行按自身工作根加载有界项目指令，以绝对来源路径区分目录快照。
- `context-management`: 区分各目录的文件状态和结果缓存，归档父任务需要的证据后才允许清理对应目录。
- `session-persistence`: 记录工作树归属和成果状态，登记归档证据，恢复不自动重跑子任务或接管仍活动的目录。

## Impact

- 涉及 `src/mewcode/agents/`、`tools/`、`permissions/`、`hooks/`、`prompts.py`、`instructions.py`、上下文与会话持久化模块；预计新增专责 Worktree 管理模块，避免将 Git 生命周期集中到入口文件。
- 使用现有 Git 命令行，不引入用于替代 Git Worktree 的第三方依赖；Git 版本及工作树专属配置兼容策略需要在设计中明确。
- `agent` 工具参数保持不变；新增角色字段与子结果中的工作树元数据。已有未声明隔离的角色不需要迁移。
- 需要同步 README 和验收清单，自动化覆盖路径、恢复、权限、取消及清理边界；实现后按仓库要求使用真实模型和 tmux 做本次端到端验收。
- 本变更规划包括 proposal、design、10 份增量规格和实施任务。工程默认值在 design 中明确记录，供整体评审；规划完整不表示实现、测试或端到端验收已经完成。
