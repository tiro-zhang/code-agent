## Context

动机见 [proposal.md](proposal.md)。本变更满足跨组件和性能复杂度条件，需要技术设计。

当前前端为 React 19、TypeScript、Vite，正文通过 react-markdown、GFM 和 rehype-highlight 展示。App 同时管理服务状态、草稿、历史、事件循环和控制操作；草稿编辑使整个消息列表更新。完整状态经 JSON 解析后产生新的消息对象，现有 SSE 循环逐事件等待 synchronize，且没有把状态快照的覆盖序号用于省去后续重复读取。mutate 在回执确认和状态同步后仍等待 load_sessions，期间 working 继续禁用停止等入口。折叠的 details 也会构建正文、差异和结果子树。

探索阶段的测量仅用于定位，不能作为优化后的浏览器验收：

| 测量条件 | 观察结果 |
| --- | --- |
| 生产 React + jsdom，100 条每条约 1.2 KiB、含代码块的历史 | 每次草稿编辑执行 100 次 Markdown 渲染，更新中位数约 306 ms |
| 实际 App + 模拟 API，100 个积压 SSE，首次状态读取已覆盖全部事件 | 仍发出 100 次状态请求；256 KiB 历史对应约 25 MiB 响应 |
| 生产 SSR，单条约 128 KiB、含较多代码块的消息 | 完整渲染中位数约 118 ms，未计浏览器布局 |
| 实际 App + 故意延迟的模拟会话列表响应 | 发送回执已确认、运行状态已同步后，停止仍禁用至列表读取结束 |

现有主规格要求草稿版本保护、运行期间可浏览与起草、停止与审批的真实状态、快照替换及实例隔离。性能优化必须同时满足这些合同。

## Goals / Non-Goals

**Goals:**

- 将本地编辑、权威控制状态和较重的正文展示分成独立更新路径。
- 减少重复解析、完整状态请求和折叠详情构建，用真实生产浏览器复核收益。
- 对在途事件、迟到响应、分页刷新和完成时格式化建立可测试的处理边界。

**Non-Goals:**

- 本轮不引入新的公开增量协议、全局状态管理依赖、聊天历史虚拟列表或服务端存档索引。
- 不改变项目执行槽、操作幂等、权限、模型请求、事件缓存限额和断连不取消语义。
- 不改变后台任务所有权或将界面流畅误报为真实任务已经停止。

## Decisions

### 1. 按会话管理草稿，仅输入区订阅编辑变化

新增职责单一的草稿模块，保存项目、会话和当前标签页对应的 text/version；输入组件只订阅当前会话。App 通过稳定接口读取最新草稿、设置建议文本和按接受回执确认提交，不在每个按键时 set_drafts 驱动工作台更新。现有 Composer 可继续负责输入法、快捷键、补全和大小校验。

草稿存储仍沿用 sessionStorage 的现有键和即时保存策略，存储失败保留内存文本及可见提示。回执清理必须比较会话、版本和提交文本；切换会话或继续编辑后，旧回执只能作用于原提交版本。服务重启保留草稿，但不自动发送。

选择局部订阅而非给整个 App 添加大量 memo，是因为输入本身不需要更新历史、执行轨迹和项目控制。暂不延迟草稿持久化，以免增加刷新丢失窗口。

### 2. 以实际正文和展示模式缓存 Markdown

先隔离安全正文组件，稳定插件和代码块组件定义，并按 text 与展示模式复用解析结果。只按消息对象引用使用 React.memo 无法处理新 JSON 快照；只按 ID 或文字长度比较则会漏掉正文替换。完成标记、截断提示、结果身份和工具状态独立按实际变化更新。

生成中统一使用可选择、可复制的纯文本轻量正文；不执行 Markdown 高亮。普通正文显示更新合并到最多每 100 ms 一次，最终正文、完成身份和缺失说明不会因限频遗失。收到完成快照后先显示完整轻量正文与真实状态，再自动调度一次完整安全 Markdown 和高亮，不要求用户重新请求模型或手动加载最终正文。

最终格式化使用较低优先级并按正文版本取消过期结果；优先处理已经到达的输入和控制更新。调度只能改变工作的执行时机，不能使单次同步解析自动变快，因此完成过渡的最大交互延迟和主线程长任务必须单独记录，不以延后启动冒充消除解析成本。

选择轻量生成、完成后增强，而非对每片段完整格式化，是用户已确认的体验取舍。复杂的增量 Markdown 解析暂不引入。

### 3. 折叠详情按需构建并保留有效浏览状态

历史上下文、工具详情、思考、参数和 diff 在首次展开时才构建重正文。状态摘要、调用身份、截断提示和待审批入口始终更新。结果读取仍只在明确操作时访问已登记接口。

首次展开后的已读分块、审批审阅进度和代码复制状态不因无关快照重新挂载。详情与正文缓存跟随消息驱逐、会话／实例／运行代次变化释放，不保留无界全局渲染缓存。审批仍须完整审阅原分区，折叠工具展示不能代替审批预览。

选择按需构建而非仅用 CSS 隐藏，是因为隐藏并未避免当前的 JSON 展示、差异分行和组件构建工作。

### 4. 由单一调度器合并状态读取

从 App 的逐事件 await 循环中拆出同步调度职责。事件解析继续推进，普通 text_delta／thinking_delta 通知只更新待同步最高序号；同一服务实例最多一个状态请求在途，普通通知最多每 100 ms 发起一次读取，无新事件时不持续请求。已有快照覆盖的普通事件不再产生状态读取。

调度器分别维护：

- received_seq：同一实例实际消费或通过明确替换基线恢复的事件序号，用于重连。
- snapshot_seq：已接受权威状态的覆盖序号，用于判断是否需要再次读取。
- target_seq：已知需同步的最高序号；另有独立的会话列表刷新标记。
- 实例／请求代次：用于丢弃旧服务、旧会话和卸载后的迟到结果。

请求返回后若 target_seq 仍高于 snapshot_seq，调度一次后续读取，即使后续没有新事件也能追上最后的通知。有限的请求失败采用现有重连／轮询恢复和可见错误，不做无间隔重试。

不能把 received_seq 无条件推进到 /state 的 snapshot_seq：状态接口不包含会话列表，也不能证明被越过的列表通知已处理。事件去重与领域通知处理先依据 received_seq；普通状态读取再依据 snapshot_seq 省略。sessions_changed 即使已被状态快照覆盖，仍登记一次合并的列表刷新；snapshot_replace、事件窗口失效和重新建立基线时额外刷新列表以补足缺失通知。

保留现有 /state 和 SSE 合同，避免直接把私有 AgentEvent 正文作为公开增量。与公开差量协议相比，此选择改动较小，但完整快照传输仍随历史大小增长。

### 5. 权威控制状态及时更新，正文和列表刷新不阻挡控制

审批通知、状态通知、任务结束等关键事件，以及明确用户操作后的状态核对，升级待同步请求优先级并绕过普通正文等待；多个关键通知仍共用在途读取，必要时在其完成后立即补读。优先级不承诺远端服务的响应耗时。

接受快照时先更新权威状态引用和 runtime、approvals、连接／错误信息；正文投影可合并展示。控制提交读取最新权威实例、会话、代次和 state_version，不能读取延后的展示状态。结束快照触发原有一次性历史首页刷新，继续保留分页游标、请求代次和阅读锚点。

操作的 working/pending 在原回执确认和必要状态核对结束后按实际结果更新；会话列表使用独立刷新状态及错误提示，不继续持有操作入口。未知回执、身份冲突、旧实例和真实项目忙碌约束继续生效。列表失败不把已接受任务标为失败，也不自动重发任务。

选择拆开刷新状态而非放松按钮权限，是为了减少无关等待，同时继续由实际回执和服务状态决定操作是否可用。

### 6. 用确定性计数和生产浏览器延迟验收

新增针对真实组件与调度边界的回归：草稿输入期间既有历史的 Markdown 解析次数为 0；100 个普通积压事件被首次快照完整覆盖时仅需 1 次额外状态读取；请求期间的新事件有后续同步；被覆盖的列表通知仍处理。

工程默认值：普通同步／正文合并窗口为 100 ms，超长压力正文取 128 KiB。生产浏览器参考场景使用 100 条约 1.2 KiB、每条含 10 个小型 Python 代码块的历史，以及每秒 40 条普通正文通知持续至少 10 秒。至少采样 50 次输入和各 20 次导航、停止操作；停止样本使用独立可复位场景，不对已取消任务制造重复工作。

以同设备、同浏览器版本、相同数据和生产构建比较改动前后。默认验收目标为输入到下一可见更新、导航点击到选中状态更新、有效停止点击到请求发出分别 P95 不超过 100 ms；不计历史远端读取完成、服务响应和工具实际收尾时间。报告各自 P95、最大值、正文完成格式化附近的样本与主线程长任务，不能只报平均值或删除慢样本。

现有浏览器测试使用 Vite 开发服务器，需为性能测量补充加载正式构建的入口；功能测试可继续使用原入口。SSR／jsdom 计数用于回归解释，不能替代真实浏览器、真实 Web 模型流程和 tmux 终端回归。

## Risks / Trade-offs

- [轻量流式正文暂不呈现格式和高亮] → 保留原文和复制能力，完成后自动恢复安全完整展示，文档说明此变化。
- [完整快照仍有大正文传输及 JSON 解析开销] → 合并请求并记录响应字节；如果收益不足，提出独立公开增量协议变更，不能把本轮描述为已经消除此成本。
- [最终格式化仍可能产生长任务] → 缓存后只处理变化正文，先提交控制与轻量内容；纳入真实浏览器的完成过渡样本，出现阻塞时针对解析／挂载热点优化，不能仅增加等待时间。
- [合并或跳过事件漏掉最后状态、列表刷新或审批变化] → 分离游标和领域标记，覆盖在途追加、明确基线替换、失败恢复与优先事件测试。
- [新状态对象使缓存无效，或错误缓存隐藏状态变化] → 以实际展示数据判断失效，覆盖同 ID 等长替换、完成／截断变化和工具状态更新。
- [草稿局部状态与外部回执不同步] → 单一版本源和按会话通知，复核切换、刷新、建议填入、IME、迟到及未知回执。
- [机器差异影响绝对延迟] → 记录操作系统、CPU、浏览器、构建摘要和测量口径，同机比较，不用减小语料或删除慢样本取得通过。

## Migration Plan

1. 在既有测试旁加入失败回归和可复现测量入口，固定语料与口径。
2. 先隔离草稿与缓存／轻量展示，再接入同步调度和独立列表刷新状态，逐步运行对应回归。
3. 更新 README、本次 checklist 验收章节和 docs/validation/web-performance/ 材料；所有通过、失败和未执行均记录本次证据。
4. 重新构建前端与 manifest，验证 wheel／sdist；完成真实授权模型 Web 流程和 tmux 终端端到端验收。
5. 无存档格式或接口迁移。回滚时恢复配套前端源码、正式静态资源和 manifest，不将回滚解释为取消或回放已接受任务。
