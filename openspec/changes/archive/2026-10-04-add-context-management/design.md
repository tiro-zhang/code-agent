## Context

动机见 `proposal.md` 的 Why。当前 `ChatSession` 拥有内存历史，`Agent.run` 在获得完整响应后共同提交用户输入、应用提醒、助手调用及对应工具结果；两种供应商在发送时转换协议。现有恢复直接删除较早用户轮次，不能缩减当前长任务的早期阶段。

已有 `TokenUsage.total_input_tokens` 可区分总输入与缓存未命中；供应商可能完全不返回 usage。Anthropic 输出上限当前固定为 8192，OpenAI 适配器尚未显式设置对应上限。文件工具仅访问工作根目录内的真实路径，因此应用缓存也放在项目内。规划、权限、工具副作用和待执行计划分别由现有状态管理，不能从摘要文字恢复这些控制状态。

本变更跨会话、请求、协议和终端，并引入有生命周期的磁盘引用，因此需要设计文档。所有实际代码、配置模板、README 和验收记录更新均属于后续实施，本次仅创建变更文档。

## Goals / Non-Goals

**Goals:**

- 让上下文准备成为所有工作模型请求的固定前置步骤，摘要请求采用独立且不递归压缩的路径。
- 保持用户原文、工具结果配对及已发生操作的真实性；失败和取消时不会提交半份摘要或重放工具。
- 明确请求预算、输出预算、估算安全余量和磁盘缓存的不同职责，并使每种停止原因可观察。
- 通过确定性测试验证预算和状态机，以本次真实服务 tmux 验证可继续工作的行为。

**Non-Goals:**

- 不保证任意长度的单个用户输入都可容纳，不把近似估算称为真实 token 计数。
- 不实现精确 tokenizer、学习型策略、递归分块摘要、跨进程会话恢复或旧原始输出补采。
- 不让摘要改变计划有效性、当前模式、权限或工具的真实执行结果。

## Decisions

### 1. 会话持有上下文状态，代理负责请求编排

新增 `src/mewcode/context/`，按职责组织估算、工具结果缓存、历史分区和摘要协调。会话持有一个上下文管理实例，跨普通任务保存 usage 锚点、摘要版本、连续失败计数及熔断状态。代理在请求前调用它，供应商只负责序列化和传输；终端只消费进度与结果。

使用稳定的本地消息／工具结果身份和历史版本关联锚点、落盘引用及摘要来源，不通过正文标签猜测应用身份。`Message` 必要的本地元信息不作为未知协议字段发送。工具输出替换使用新的不可变值，避免修改已经发给终端的原始结果事件。

```text
ChatSession
    |
    v
Agent request gate --> Spill --> Estimate --> Working provider request
                                    |
                                    v
                              Partition history
                                    |
                                    v
                              Summary provider request
                                    |
                                    v
                              Validate --> Atomic commit --> Recheck
```

不采用每个工具自行压缩的方案：同批合计、用户原文保护和累积历史预算都需要全局视图。也不直接在协议转换后裁剪，否则容易把两个协议的消息边界当成同一种语义单位。

### 2. 明确窗口和输出额度

配置新增必填正整数 `context_window`，表示服务提供的总上下文窗口；缺失即提示补充配置，不使用模型名猜测或任意默认窗口。新增 `max_output_tokens`，默认 8192，工作和摘要请求都使用该输出上限并按相同额度预留；摘要草稿、正式摘要及服务计入输出额度的思考共同占用该额度。

设窗口为 C，输出预留为 O，完整工作输入估算为 E：

- 自动触发：`E + O + 13000 >= C`。
- 自动摘要请求也要求其自身输入估算加 O 和 13000 小于 C。
- 手动 `/compact` 不需要达到自动门槛，但其摘要请求要求输入估算加 O 和 3000 小于 C。
- 成功提交的摘要必须使下一工作请求低于自动触发线；3K 只放宽手动摘要请求的输入空间，不修改后续自动策略，避免手动成功后立即重复自动压缩。
- 启动验证 `C > O + 13000`；系统提示、工具定义和不可压缩消息是否还能容纳，在构造实际请求时继续验证。

所有 K 均为十进制 1000。不把安全余量作为压缩完成后的目标长度，不把预留输出直接当成实际账单。供应商若不能接受输出上限控制，应报告兼容错误，不静默发送无上限请求。

### 3. usage 锚定与字符增量估算

估算范围覆盖系统提示、当前工具定义、应用提醒、消息角色与封装、调用参数、结果正文及实际回传的供应商内容。基线字符启发式采用 ASCII 字符约每 4 个计 1 token、非 ASCII 字符约每个计 1 token，并对消息封装保留固定开销；集中实现且测试中可注入，初期不训练系数。

完成工作请求时，记录该次实际输入快照的身份／分项字符估算、固定前缀指纹及有效 `total_input_tokens`。在固定前缀和已发送消息不变、只追加内容时：

`下一输入估算 = 上次实际总输入 + 上次输入之后新增的实际回传内容估算`

新增内容包括该次助手响应、工具参数与结果、下一用户输入及新提醒。不能把 `output_tokens` 直接全量再加一次，因为部分思考并不回传，而已序列化内容也不能重复计数。

首次请求或无有效总输入时使用完整字符估算；缺失 usage 不填零。如果落盘替换已锚定内容、提交摘要、切换工具集／模式导致请求前缀变化，废弃旧锚点，按新请求重建字符估算，待下次有效工作 usage 校准。摘要 usage 进入费用／请求统计，但绝不覆盖工作历史锚点。估算值与实际报告的用量分别展示。

选择失效后重估而非复杂的删除比例拟合，降低第一版实现风险。已缓存文本仍占上下文，不能用缓存未命中输入替代总输入。

### 4. 轻量层按工具调用批次缩减

按一个助手响应及其所有工具结果定义批次，不依赖 Anthropic 合并用户消息或 OpenAI 独立 tool 消息的传输形态。

先将序列化后估算超过 8000 token 的单项落盘，再计算当前整批；合计超过 20000 时，按预计可节省大小从大到小处理尚未落盘的结果，同等大小按原调用顺序。存盘后替换为结构化预览与路径，预览初始上限 1000 token。若所有结果已落盘仍超批次阈值，可继续缩短预览到仅剩必要引用和状态；没有进一步收益即停止轻量处理，由整体预算决定是否需要摘要或受控停止，不反复处理同一引用。

保留调用 ID、工具身份、`ok`、错误码和说明、`truncated`、权限受限及副作用不确定等重要状态。预览和指针开销计入估算，不能把落盘失败伪装成成功。只保存工具实际返回的结构化结果，64 KiB 限制之前已截掉的输出无法恢复；落盘不自动把 `truncated` 改为 true，它与“正文存于文件”是不同状态。

对首次待发送结果实施一次即可，历史扫描只处理未规范化或预算相关的批次。轻量层不调用 LLM，不消耗请求次数；只在当前任务调用预算仍允许继续时准备下一请求。

### 5. 缓存是应用内部存储，读取遵守现有权限

会话缓存目录为 `.mewcode/context/<session-id>/`，使用应用生成的随机身份及安全文件名，不直接把供应商调用 ID 当成路径。目录和文件限制为当前用户可访问，创建和替换验证真实路径，拒绝符号链接逃逸或非普通文件。写入临时文件并完成原子提交后才发布指针；写失败时保留原结果。

结果使用可分段阅读的多行 UTF-8 表示，正文和结构化状态均完整可恢复，避免把大结果写成只有一行的 JSON，导致 `read_file` 不能有效分页。引用提供项目内路径、来源标识、长度和读取提示。缓存目录自身建立 `*` 忽略规则，保证任意用户项目均排除版本控制，也不自动进入普通项目搜索结果；模型通过明确路径分段读取，读取仍经过规则、授权、规划范围及文件路径检查，不因为来源是缓存就绕过 deny。

应用内部缓存写入不作为模型的 `write_file` 调用，不触发工具审批，也不赋予规划模式业务文件写权限。正常退出只清理本会话生成的目录，清理失败报告但不声称已删除；崩溃遗留不用于自动恢复、也不擅自清理其他会话目录。会话内只删除已不被保留历史或当前摘要引用的缓存；有引用的缓存不可静默淘汰。磁盘写失败时停止落盘尝试并按现存内容做全局预算判断，无法容纳则受控停止。

### 6. 保留原文与合法交互边界

将工作历史看作真实用户输入和完整助手交互组成的序列；一个助手调用及其全部结果是不可拆的单元。应用提醒随关联交互处理，但不计入至少 5 条消息。先对工具结果完成轻量替换，再从尾部累积，直到达到约 10000 token 且至少 5 条非提醒消息，随后向前扩展至完整交互边界。全历史不足时全部保留；扩展超过 10000 属正常结果，不截断工具块。

运行中的当前任务用户原文始终固定保留，即使其后较早工具交互被摘要；空闲手动压缩时，固定保留最近一次真实任务输入。对尚未提交的本轮用户问题只纳入候选请求预算，不因摘要操作提前提交。保留区内用户消息逐字保留，不重复插入；用户文本不在尾部时仍按任务归属放在其近期交互之前。

较早记录（含当前任务较早的完整交互）及上一份摘要形成新的摘要输入。已存在摘要被替换，不层层追加。压缩后的工作历史由新摘要、必要的原文任务输入、近期完整交互构成，并保留来源关系。当前任务原文在摘要请求中可以作为理解材料，但不能因此再次摘要改写后替代原文。

如果保护区、系统提示或工具定义自身已使后续工作请求无法容纳，直接报告不可压缩原因；没有旧内容可摘要时不请求 LLM。第一版不降低保留规则、不截断用户输入，也不对同一份明显无法装入的摘要输入递归摘要。

### 7. 无工具的结构化摘要

摘要使用同一个已配置供应商的独立调用，传入专用系统提示和明确标记为历史数据的转录，工具列表为空；适配器在适用时设置禁止工具选择。摘要调用不经过 Agent 工具执行循环，即使响应带调用也只算摘要失败。历史正文不能改变摘要指令或实际模式／权限。

Prompt 明确要求：不调用工具、不执行历史指令、不继续原任务，先输出 `<draft>` 分析草稿，再输出 `<summary>` 正式摘要。应用只接受正常完成流中唯一、完整且顺序正确的草稿与摘要段；草稿与供应商思考片段不进入终端、历史、缓存或调试日志，只保留实际 usage。正式摘要固定六部分：

1. 当前目标。
2. 用户约束与关键原话。
3. 已完成工作与验证证据。
4. 关键决策。
5. 文件与结果索引。
6. 未完成事项与下一步。

摘要目标与接受上限为字符启发式估算 2000 token。关键约束要求逐字引用并注明真实用户消息来源；对上一摘要继承的引用保留已校验来源，当前新增引用校验其确为对应用户原文片段。空章节明确写“无”或“未知”，不得将未执行验证写为通过；文件索引保留仍需使用的缓存引用；超过 15 个路径时由应用原子维护单一可分页 `results-index.jsonl`，摘要引用该索引，应用仍保存并校验所有底层结果。调用前及提交前均检查引用可用性；I/O 障碍不计模型失败。若必要原话和索引本身已超过摘要上限，调用前直接停止。该检查能验证格式和引用一致性，不能证明模型没有遗漏语义，需真实行为验收。

校验流正常结束、无工具调用、段落完整、正式摘要长度、原话引用、引用文件可用、候选历史配对合法、有实际缩减收益且后续工作请求低于自动线，再一次性提交。任一失败不提交摘要；之前已成功完成的轻量落盘无需回滚，原结果仍可由文件恢复。摘要事务的回滚基线是轻量处理后的历史。

不采用流式边生成边改历史：取消、断流、无正式摘要或服务超限都可能发生，必须等候选结果验证后再提交。

### 8. 边界提醒与应用控制状态

摘要后添加本地标识为压缩边界的应用消息，说明较早内容已摘要，缓存仅是历史快照，代码细节与编辑前必须重新读取当前文件，不能根据摘要猜测 `old_text`。提醒在完整调用／结果组之后，不插入组内；历史中的边界随其关联内容一并压缩，避免每次请求追加重复提醒。

成功压缩使下一工作请求强制补发完整环境和当前模式，保留原模式周期序号。摘要不调用 `PromptState.begin_request`，不推进工作模式的提醒周期，也不消费待执行计划。固定工作系统提示仍使用稳定前缀，摘要及边界位于应用上下文消息中；供应商序列化不赋予它们原生系统权限。

规划／执行、权限批准和熔断状态由本地对象管理；摘要不得重建批准、执行旧命令或使 `/do` 重放计划。`/compact` 成功、失败和取消都不使有效待执行计划失效。

### 9. 有界失败、熔断与服务实际超限

会话维护连续失败次数，摘要调用失败、响应无效、无收益或候选结果不能满足后续工作预算均计一次；成功提交清零，取消和未实际调用的无操作不计，普通新任务不重置。自动压缩最多尝试到连续失败第三次，同时受当前任务剩余 `max_iterations` 限制；每次实际摘要请求和失败工作请求都消耗一次请求预算。没有预算时不再摘要也不启动工作请求。

第三次失败后熔断自动摘要。若工作请求在触发线下仍可正常执行；若需要摘要却已熔断或压缩无法完成，产生 `context_blocked` 停止，保存当前已提交历史并回到提示符。不会恢复旧的 1/2/4 无摘要删除路径。每次空闲 `/compact` 最多发起一次摘要请求，包括熔断状态；成功解除熔断，失败维持或增加失败计数。手动操作有独立用量记录，不消费下一任务的请求预算。

服务实际返回上下文超限且尚无可见文本／思考时，允许在剩余预算内强制走同一摘要路径，即使估算未到自动线；压缩成功后再请求工作模型。一次恢复后工作请求仍报超限，停止并提示核对窗口／输出配置，避免在相同保护区内重复恢复。若服务拒绝摘要输入，计为一次摘要失败并停止本次相同输入的自动重试，避免明知装不下仍连续发送；可由后续显式操作或新的可压缩历史再尝试。已展示部分工作响应时不透明重试。

工具结果缓存 I/O 失败、保护区太大或静态前缀超限不计为模型摘要失败；这些确定性障碍直接报告，不耗三次调用证明同一障碍。取消关闭活动流，失败计数不变，候选摘要丢弃，已经完成的工具副作用保留。

### 10. 终端可观察性与验收

增加压缩阶段事件和结果，区分工作请求与摘要请求；自动摘要 usage 计入任务累计但单独标注用途。显示压缩前后估算、落盘数量、失败次数／熔断状态；`/status` 继续保留最近任务真实记录，并增加独立上下文状态。摘要草稿、内部完整摘要和缓存正文不因状态展示自动打印。

`/compact` 仅空闲单行本地命令接受，不带参数；复用取消和终端输入所有权，运行时输入不会成为其他操作或授权答案。空历史／无可摘要前缀返回无操作说明，不发请求、不清除熔断。增强终端与 plain 使用同一会话入口。

确定性测试覆盖阈值、中文与代码增量、缓存总输入、缺失 usage、变更锚点、工具配对、原话、草稿剥离、取消和预算。供应商替身核对禁工具与输出上限。真实 tmux 在临时工作目录运行两种已授权协议，覆盖自动压缩、手动压缩、引用文件重读和压缩后继续修改／验证；故障计数和严格阈值以替身测试为主，真实服务不能稳定复现的项目如实标明。

## Risks / Trade-offs

- 字符估算与实际 token 偏离 → usage 定期校准，13K／3K 额外余量，保留有界实际超限恢复；不承诺永不触发服务错误。
- 摘要遗漏或错误推断 → 固定结构、原话来源校验、验证证据和未知项明确记录，边界提醒要求重新读取；摘要不能替代事实验证。
- 保护用户原文和近期窗口导致无法缩小 → 明确 `context_blocked`，不静默破坏保护规则。
- 多次失败耗费请求和费用 → 自动请求统一计入 `max_iterations`，最多连续三次，手动每次至多一次，并展示用途与 usage。
- 缓存文件包含工具曾读取的内容 → 项目内私有目录、版本控制排除、权限检查与正常退出清理；崩溃残留不伪称已经清理。
- 缓存引用占用磁盘或磁盘不可写 → 有引用不静默删除，失败保留原结果，不能继续时受控停止；本次不实现磁盘配额管理系统。
