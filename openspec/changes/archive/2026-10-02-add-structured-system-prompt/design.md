## Context

动机与范围见 [proposal.md](proposal.md)。现有 `Agent.run()` 用 `EXECUTE_PROMPT` 或 `PLAN_PROMPT` 整体选择系统提示，并在任务开始时筛选允许工具；`ChatSession` 保存模式、历史和有效计划。历史裁剪通过 `Message.role == "user"` 定位真实任务起点，完整工具响应和结果在单一入口提交。

Provider 当前接收 `system_prompt: str`。OpenAI 将其放入开头的 system 消息，Anthropic 使用顶层 system 字段。两个适配器已经读取部分缓存字段，Collector 与任务聚合也保留读写计数，但终端只展示基础输入和输出；原生 Anthropic 的 `input_tokens` 不包含缓存读取和创建，不能直接作为命中率分母。

用户已确认：DeepSeek 为真实验收基准；动态内容采用应用生成的标签上下文，不要求原生 system 权限；注入轮次按实际模型请求计数。默认周期采用讨论中的 5 次，作为后续人工评估可调整的内部策略值，不增加 `.env` 配置项。

当前示例和已记录验收使用 `deepseek-v4-pro`、Anthropic 兼容地址。DeepSeek 官方模型能力示例将该模型标为 `leading-only`，不能依赖历史中的 system 消息更新指令。DeepSeek 会忽略 Anthropic 缓存标记，使用自动公共前缀缓存。

来源（2026-10-01 核对）：[DeepSeek 模型能力](https://api-docs.deepseek.com/api/list-models/)、[Anthropic 兼容说明](https://api-docs.deepseek.com/zh-cn/guides/anthropic_api/)、[缓存与计数](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)、[Claude 缓存前缀](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[OpenAI 缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)。

## Goals / Non-Goals

**Goals:**

- 固定提示构建、应用上下文、协议序列化和缓存统计有各自明确的输入与输出。
- 运行时提醒可以跨真实用户任务保持周期，也能与既有预算、提交、取消和裁剪边界衔接。
- 为协议字段缺失和供应商计数差异提供可靠的解释，验证证据能追溯到实际响应。

**Non-Goals:**

- 建立通用提示模板框架、动态插件加载或新的服务发现层。
- 给标签提醒增加原生系统权限，或新增“未读取则禁止编辑”的执行器状态追踪。
- 改动计划有效性、工具算法与并发、权限审批或会话持久化。其余范围见提案。

## Decisions

### 1. 固定文本、环境快照与提醒策略分别承担一个职责

建议新增轻量提示模块，例如 `prompts.py`；顺序由显式列表表达，每个模块有稳定标识和文本，拼装函数只以一个空行连接非空内容。七个固定模块的职责如下：

| 顺序 | 模块 | 主要内容 |
| --- | --- | --- |
| 1 | 身份 | MewCode 的编程助手角色、以用户任务为目标 |
| 2 | 系统约束 | 冲突处理、工具真实边界、外部内容是数据、结果须据实说明 |
| 3 | 任务模式 | execute/plan 的定义、当前状态取最新应用提醒、旧提醒仅是历史阶段上下文 |
| 4 | 动作执行 | 按需理解与探索、沿用项目代码约定、执行后核对结果与适当验证 |
| 5 | 工具使用 | 专用工具选择、先读后改、错误后调整、允许范围 |
| 6 | 语气风格 | 中文、直接、简洁，说明事实与未完成事项 |
| 7 | 文本输出 | 进度沟通、完整计划、执行结果、文件引用和验证状态 |

固定规则不写“当前是规划模式”或运行环境值。模块排序表示组织顺序；系统约束和任务模式中显式说明冲突规则，避免把同一消息里的前后位置误当作原生权限层级。

环境快照在会话创建时从 `ToolContext.root`、平台、Python 版本及启动日期采集；日期标为会话启动日期，不能暗示它在跨日后仍是当前日期。自定义指令、已激活 Skill、长期记忆保留显式文本参数或等价插入位置，放在环境之后；默认空值，不实现加载和发现。它们与环境一起走补充消息，不放入固定 system。完整上下文中的当前模式说明位于这些补充段落之后，明确当前请求许可。

固定内容不含时间戳、请求 ID、模式计数或配置密钥。选择纯函数与明确顺序而不引入模板引擎，可降低无关空白或遍历顺序改变前缀的风险。

### 2. 本地增加应用上下文身份，线上映射为普通内容

在协议无关的数据层为应用提醒增加独立种类，例如扩展 `Message.role` 为内部 `context`。其内容保存实际发送的标签文本；该内部种类只能由应用构造，Provider 不向服务发送 `role=context`，也不通过扫描用户/工具正文中的标签判断身份。

Provider 的 `system_prompt` 参数可以继续接收稳定字符串，无需为整个请求再增加一套框架接口。`tool_messages.py` 增加内部 context 的明确映射：

- OpenAI：在当前真实用户消息或全部 tool 结果之后，将 context 映射为普通 user 内容；不在 assistant 调用与配对 tool 消息之间插入提醒。
- Anthropic：将 context 映射为 user 的 text 块；工具续接时先排列紧随助手的全部 `tool_result` 块，再排列提醒文本。沿用合并相邻 user 消息的逻辑，保持助手原始思考、签名和其他块不变。

线上标签固定为 `<mewcode-context>`。完整内容按环境、自定义指令、Skill、记忆、当前模式说明排列；精简内容只保留当前模式和必要约束。普通用户问题保持原文，内部提醒不打印为新的 `你>` 输入。

```text
Stable prompt + Stable allowed tools
                  |
                  v
Real user task --> Runtime context --> Assistant response --> Tool results
                                           |
                                           v
                           Next runtime context --> Next response
```

这保留了真实问题与应用数据的本地区别，并兼容现有 DeepSeek 模型。直接追加原生 system 会依赖模型能力；把所有动态状态写进开头 system 会改变后续历史前缀，均不采用。普通内容形式的提醒仍是模型行为指引，真正的模式限制继续依靠三工具筛选和执行入口拦截。

### 3. 在会话中维护模式周期，预算继续属于单次任务

为 `ChatSession` 持有的提示状态记录当前模式、模式请求序号、环境快照，以及是否必须补发完整说明。它可由轻量策略对象实现；`Agent` 在统一请求入口调用策略，不在 CLI 或 Provider 内各自维护计数。

模型请求序号在实际开始 Provider 请求时递增，不能仅因构造候选消息递增。已经发出的失败请求和恢复重试均计数，SDK 保持现有 `max_retries=0`。发送前取消、预算耗尽、裸 `/plan`、无效 `/do` 均不会额外增加次数。

默认完整条件为：序号 1，或者 `(序号 - 1) % 5 == 0`，或者待补发标志为 true。其余精简。完整包包含环境和当前模式的完整说明；plan 包含三个允许工具、禁止写入和 shell、最终完整计划要求，execute 明确允许执行当前任务并将历史规划限制限定于过去阶段。

| 事件 | 模式周期 | 下一请求 |
| --- | --- | --- |
| 会话初始化 | execute，序号 0 | 第 1 次完整 |
| 同模式普通新任务 | 不重置 | 按原周期；任务预算另行重置 |
| `/plan` 或 `/plan <任务>` | plan，序号 0，标记待补发 | 第 1 次完整；裸指令不请求 |
| 再次显式 `/plan` | 开始新规划周期，序号 0 | 第 1 次完整 |
| 有效 `/do` | execute，序号 0，标记待补发 | 第 1 次完整 |
| 无效 `/do` | 不变 | 不请求 |
| 历史裁剪 | 序号不重置，标记待补发 | 强制完整 |
| 发出的请求失败或中断 | 已消耗的序号不回退 | 尚未提交的完整包仍需补发 |

准备任一完整包时将待补发标志置为 true，成功进入历史时才清除；因此周期性完整包失败后也会补发，普通精简包的失败不单独重置周期。裁剪补发不会重新定义第 6、11 次的节奏。这使“每次模型请求”与用户任务预算各自准确，且首次完整说明失败后不会假定模型已获得它。

### 4. 提醒随完整响应提交，不修改历史记录

每个请求准备一个候选 context。在该请求获得完整助手响应后，沿用现有唯一提交入口：

1. 首次提交当前任务时保存真实用户问题。
2. 保存该请求实际使用的 context，再保存完整助手响应。
3. 有工具调用时，在调度或取消收尾后补齐按调用顺序排列的所有结果，再进入下一请求。

无工具的完整答复提交后仍以助手消息结尾，`ChatSession` 获取最终计划的语义不受影响。完整工具响应在工具处理期间被取消，context 与完整调用和实际/取消结果共同提交；不完整模型响应的候选 context 随响应一起丢弃。

上下文裁剪仍按真实 user 定位任务起点。内部 context 不生成新的起点，与其所属任务内的所有阶段一起删除；当前任务保持整体。裁剪后使用会话保存的环境重新构造新的完整包，保留下来的旧包原样回传。

选择不可变的已提交提醒，而不是每次在历史中替换旧提醒，可保持成功请求的前缀增长，也避免改写 Anthropic 思考续接之前的消息。失败候选的丢弃沿用现有历史可靠性要求；失败请求本身消耗的序号仍保留。

### 5. 缓存策略由实际服务决定，工具许可保持原状

| 实际服务 | 本章策略 |
| --- | --- |
| DeepSeek 官方 Anthropic 地址 | 稳定 system 和工具；追加标签消息；使用服务自动缓存，不依赖 `cache_control` |
| 官方 Claude API 地址 | system 转为合法 text 块，在稳定内容末尾添加 `cache_control={type: ephemeral}`；默认 5 分钟；其前方工具随前缀一起缓存 |
| OpenAI Chat Completions | 保持 system 和工具前缀；沿用流式用量；不引入新模型专有缓存参数 |
| 其他兼容地址 | 保持基础协议，不未经确认发送官方专有字段；返回了已知用量则读取，否则标未知 |

沿用 DeepSeek 的精确地址识别方式，对官方 Claude 同样依据实际配置地址识别；协议名或模型名字不足以证明专有缓存能力。官方 Claude 的请求字段可以用替换网络传输的回归确认，真实缓存结果仅在 DeepSeek 上作为本章通过证据。

同模式下从 registry 导出的工具名称、描述、Schema 和顺序保持稳定。plan 仍为三工具，execute 仍为六工具；切换会改变工具前缀，接受相应的缓存重新建立。没有为了缓存暴露被禁止工具，也不增加动态工具移除等接口。

缓存是公共前缀复用，并非动态消息绝不会被缓存。已经提交并原样回传的历史也可以参与缓存；“不污染缓存”在本章指动态内容不改写稳定前缀。不通过增加无用提示文本追求命中，不承诺每次命中或固定节省比例。

### 6. 将总输入、命中、未命中与写入分开

保留 `TokenUsage.input_tokens` 的既有供应商基础计数语义，以兼容现有下游与部分流统计；增加独立 `total_input_tokens` 和 `cache_miss_tokens`，继续使用 `cache_read_tokens`、`cache_write_tokens`。增加或等价表达缓存分项的完整性，例如 `cache_complete`，不能仅凭基础用量的 `complete` 判断缓存是否齐全。

| 数据 | 语义 |
| --- | --- |
| `input_tokens` / `output_tokens` | 既有基础输入/输出与完整性，已知部分继续保留 |
| `total_input_tokens` | 经明确服务语义核实的总输入，用作缓存命中率分母 |
| `cache_read_tokens` | 本请求实际命中的输入 |
| `cache_miss_tokens` | 本请求未命中的输入，可能包含实际缓存写入 |
| `cache_write_tokens` | 服务明确报告的实际创建缓存输入；没有信息则未知 |
| 缓存统计完整性 | 所有需要统计的请求是否具有有效总输入及命中分项；写入未知不阻止命中率计算 |

字段读取与语义判断留在适配器。DeepSeek Chat Completions 的 hit/miss 字段在返回时可直接映射；其 Anthropic 兼容流究竟返回标准字段还是额外字段，实施时先记录脱敏的真实 `message_start`/`message_delta` usage 样本确认，再使用该接口的实际映射，不将原生 Claude 语义直接套到兼容服务。

官方 Anthropic 的总输入为 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`，未命中为 `input_tokens + cache_creation_input_tokens`；缺少必需分项且不能依据明确协议语义确定时，不把 None 当零。OpenAI 总输入来自 `prompt_tokens`，有 cached_tokens 时可计算未命中；DeepSeek 显式 hit/miss 同时出现时，总输入为两者之和。相同语义的别名选择一个权威来源，不重复相加；不能根据服务的自动缓存推测“所有未命中均已写入”。若 SDK 给未返回字段设置默认值，需依据实际返回字段判定是否已知。

Collector 合并更新时使用最后有效值，不累加同一请求的累计计数。任务聚合对每个字段保存已知合计并分别记录完整性；单次命中率为 hit/total，累计比率为 sum(hit)/sum(total)，累计任一请求缺失所需字段就显示未知或统计不完整。非负整数、分项不超过总量等必要一致性不能确认时，缓存比例未知，基础任务仍可正常完成。

终端优先展示已知总输入；总量未知时明确区分已知基础输入与未知总量。每请求和任务累计沿用现有输出入口，增加命中、未命中、已知的写入与可计算比例。基础统计完整与缓存统计完整分别表达，不把这些计数称为账单。

### 7. 行为规则在固定提示与工具描述中共同表达

在固定工具模块集中说明工具选择与先读后改，各工具描述只强调与自身有关的条件，避免把全局长文本复制六遍。`read_file` 提醒使用行范围获取相关当前内容；`edit_file` 说明读取前置指引、唯一匹配和状态变化后的重新读取；路径和内容搜索工具与命令工具共同说明专用工具优先。创建新文件不要求先读取不存在的目标。

保留现有工具参数、唯一匹配、输出上限和目录边界，规则不新增执行器读记录。`dependency_missing` 或超出专用能力等错误可指导模型在 execute 中采用其他方法；plan 的禁止 shell 约束不因这些错误改变。

### 8. 验收分别观察确定性契约、真实缓存与人工行为

确定性回归用于模块顺序和前缀、请求频率与失败/裁剪路径、历史任务边界、两协议消息配对和用量计算。既有预算、有效计划、取消及工具错误回归必须继续通过。它们不是自动化模型行为评估。

DeepSeek 实测先捕获脱敏的真实 usage 样本以落实映射，随后在 tmux 中保持同一模型、thinking、工具集和环境，执行至少 3 次连续请求。记录固定前缀一致性、实际缓存字段及值、请求序号、第一段可展示思考或文本到达的等待时间。该时间是用户可观察的首片段时间，不等同于服务内部 prefill 时延。命中必须来自真实正数计数；没观察到就记录未验证或未通过。

人工比较使用代码变更前的 Git 版本作为旧提示基线与本次新提示，固定同一 DeepSeek 配置，分别恢复样例初始文件并执行相同请求，不增加产品中的“旧提示模式”。缓存实验与人工行为比较分开；基线首轮可能已使用已有缓存，不能称为强制冷缓存。

| 场景 | 观察重点 |
| --- | --- |
| 定位函数并读取实现 | glob/search/read 专用工具选择 |
| 修复现存函数并运行断言 | 先读后改、精确编辑、实际检查与答复一致 |
| 编辑原文多次匹配 | 读取更精确上下文后调整，不反复猜测 |
| `/plan`、普通修订、`/do` | 规划仅三工具、有效计划、切换后执行和旧提醒失效 |
| 验证失败或任务取消 | 不虚构通过、不声称回滚、下一轮上下文仍正确 |
| 完整与精简提醒 | 不单独回复标签，不额外显示伪造用户输入 |

每个比较记录用户请求、工具序列、最终答复、实际结果、次数及观察结论；小样本只支持定性判断，不给出自动评分或普遍改善承诺。实施后更新 README 和 checklist，区分 DeepSeek 实测、官方协议模拟回归与未执行的真实服务验证。

## Risks / Trade-offs

- [标签提醒属于普通内容，模型可能忽略或单独回复] → 固定 system 解释作用、精简包始终携带当前模式，人工记录实际遵守率；规划权限由既有代码拦截。
- [保留旧提醒占用上下文并可能带来过时模式] → 完整包每 5 请求重复、其余精简；明确最新模式与阶段范围，随真实任务裁剪且裁剪后完整补发。
- [工具集切换和裁剪会降低历史缓存复用] → 保留安全与恢复语义，固定七模块不变，按相同模式观察复用，不追求跨全部场景连续命中。
- [DeepSeek 兼容字段与原生 Anthropic 语义可能不同] → 先核实实际 usage，缺失数据保持未知，独立保留总量与缓存完整性。
- [自动缓存尽力而为，短提示或首次公共前缀发现不一定命中] → 至少观察 3 请求并允许有限复测，报告实际结果，不将模拟或等待时间冒充命中证据。
- [模型输出具有随机性，个别场景无法证明整体质量提高] → 固定任务与初始工作区，对失败场景据实记录，限制为人工定性比较。

## Migration Plan

1. 实施前保留旧版本和固定人工场景的基线；核对实际 DeepSeek usage 字段。
