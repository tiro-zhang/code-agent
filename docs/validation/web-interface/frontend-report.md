# 本机 Web 前端实施与验收记录

日期：2026-10-07。范围：OpenSpec `add-local-web-interface` 的 5.1–5.6、6.1–6.5，以及 7.2 前端构建部分。

本报告记录 React 前端及受控 API fixture 的实际验证。真实供应商、Python 运行管理、wheel 安装与 tmux 终端验收由主流程另行记录，不能用这里的 fixture 结果代替。

## 实现范围

- `frontend/` 为 React、TypeScript、Vite 工程，依赖锁定于 `package-lock.json`。生产页面、图标、Markdown、代码高亮与样式全部从本地静态资源加载，无 CDN、远程字体或外部图片自动请求。
- 三栏工作台包含会话导航、聊天与多行输入、可收起的任务详情。窄屏提供会话及详情抽屉，支持 Escape 关闭、焦点限制与返回。模型、模式、权限、连接及项目占用均使用可见文字。
- 浏览、新建和继续是不同操作；浏览只调用历史 GET。非当前运行会话只能起草；明确继续并得到 idle 后才能发送。外部占用和不可恢复状态禁用继续；运行期间保留其他会话的浏览、新建与起草能力。
- 输入保留原始缩进、换行和末尾换行；Enter 换行，Ctrl/Cmd+Enter 发送；组合输入和 keyCode 229 不发送。空白输入与超过 256 KiB UTF-8 的输入禁发，不删除内容。
- 草稿以真实项目 key 和会话 ID 保存在标签页 sessionStorage，带独立编辑版本。仅已接受的同版本回执清除草稿。存储被禁止或容量不足时显示提示，当前内存草稿仍可编辑。
- 每个标签页使用服务签发的客户端身份及严格递增序号，提交前保存原请求和草稿版本。网络结果不明时先查询原操作；查到完成回执后按原身份、原正文再次 POST 验证其归属，账本不增加执行次数；404 后仅通过明确按钮按原身份重试。服务身份变化清除旧操作标记，保留草稿并提示查看持久历史，不自动提交。
- 一个项目 SSE 连接，按实例与序号去重。快照整体替换；其余事件通过权威 `/state` 同步，不重复拼接正文。429 时每 1.5 秒短轮询，约 15 秒尝试恢复 SSE；控制请求不依附事件连接。
- Markdown 禁用原始 HTML，图片改为文字占位，链接使用安全协议处理及新窗口隔离。代码高亮保持文本并支持复制。滚动到旧内容时不强制回到底部，显示“有新内容”。
- 工具详情显示调用、任务、轮次、状态、已捕获参数、stdout/stderr、结果、截断标记与局部 diff。支持参数为 JSON 字符串或对象。拟执行操作不会显示为完成，副作用未知有明确说明。供应商思考默认折叠；未知/不完整用量、工作及维护用量分开显示。应用上下文和历史工具正文默认折叠，保留来源标记及完整原文，主动展开才阅读。
- 待审批请求按身份绑定会话、代次和任务。目标、参数、内容、范围四分区及其分页均读完后才可批准；拒绝独立可用。提供拒绝、本次、会话和永久四决定，到期后禁用，冲突/取消/过期响应使旧卡片失效。聊天草稿不参与审批。
- 模式、权限、摘要、重置、停止和撤销会话批准使用真实控制 API；撤销显式发送 `value: "session"`。重置及撤销在界面内确认。帮助和补全来自服务定义，输入正文不由前端自行解析成命令。
- 历史支持分页去重及登记结果分块读取，兼容历史 `call` 数组/对象和嵌套 `result.result_id`。结果归属再做会话校验。单会话浏览缓存限制为 200 条/4 MiB，最多缓存 10 个会话；释放内容时提示重新打开会话阅读。服务端临时投影的截断、回收及缺失警告按原文展示。

## 构建清单与集成约定

清单文件：`src/mewcode/web/static/manifest.json`。

```text
schema_version: 1
algorithm: sha256
source_sha256: 所有 sources 条目的稳定聚合摘要
lock_sha256: frontend/package-lock.json 的 SHA-256
sources: { frontend 相对文件路径: SHA-256 }
artifacts: { static 相对文件路径: SHA-256 }
```

源码聚合按路径排序，将每项编码为 `path + NUL + hash + LF` 再计算 SHA-256。枚举排除目录名 `node_modules`、`test-results`、`playwright-report`、`.git`。产物只排除清单自身。新增源码文件也会使校验失败。对应 Python 校验由主流程/runtime 子任务实现；本报告不以 Node 校验代替 Python 启动校验。

便于主流程复核的命令：

```bash
npm --prefix frontend test
npm --prefix frontend run typecheck
npm --prefix frontend run test:browser
npm --prefix frontend run verify:build
```

## 实际接口适配与待主流程验证

- 操作成功及已入账业务错误的响应都读取 `operation.next_sequence`；认证/格式等未入账拒绝不消费本地序号。
- 回执查询按 `{status_code, body}`，未完成回执按 `{pending: true}` 处理，不把 HTTP 202 本身当成任务完成。
- `agent` 事件只作同步信号，避免依赖私有 AgentEvent 字段。`snapshot_replace` 和完整 `state` 可以直接替换权威投影。
- 实际工具参数为 JSON 字符串，初始状态为 `proposed`，均已兼容。
- 历史结果身份实际可能位于 `result.result_id`，历史调用可能为数组或对象，均已兼容。
- 已向主流程反馈临时消息身份与持久消息身份合并问题；主流程负责后端稳定 ID 映射，前端只按明确身份去重，不以相同文本猜测消息等价。
- 本子任务没有读取真实 `.env`，没有执行真实供应商、真实文件修改、MCP、CLI/tmux 或 wheel 安装验收。以上项目由主流程继续验证。
- 未修改 OpenSpec task 勾选、Python 源码或打包配置，未创建 Git 提交。

## 独立审查后的修复

本次后续 review 指出：复制浏览器标签页会复制 sessionStorage 中的客户端和操作序号，原实现遇到 `operation_conflict` 清掉 pending 后仍复用原序号，会持续冲突；`sequence_conflict` 与过期回执也没有可操作的恢复入口。

修复区分了已确认拒绝和结果不明：

- `operation_conflict` 证明当前不同正文没有被接受，登记一个独立客户端并保留草稿，等待用户再次明确发送；登记失败后保留可重试入口。
- `sequence_conflict` 保存身份故障状态并提供明确重新登记按钮，不自动提交原正文。
- `operation_expired`，包括查询原回执收到 410，保留原未确认操作和结果不明说明。用户核查当前状态与历史后，明确登记新身份才允许新操作；登记不会重放旧操作。
- 恢复状态也写入 sessionStorage，刷新不能回到旧序号的永久冲突。普通网络未知、GET 404 或 pending 回执不能绕过核查直接登记新身份。

另外，复制页可能在不同正文的拒绝响应丢失后，通过 GET 读到原页同身份的已接受回执。GET 只证明该身份存在，不能证明正文匹配。经主流程确认，`recover()` 现在先 GET，若回执已完成，再以保存的原路由、原正文、原身份 POST 复核。已有账本身份只会返回原回执或内容冲突；只有内容验证一致才确认/清除对应草稿。GET 404 仍不自动 POST。该验证不会创建新操作身份，也不增加工具或模型执行次数。

上述身份问题先分别观察 API 断言和两项 Chrome 回归失败，再实现转绿；又增加了丢失冲突响应的 API 与 Chrome 用例。最后新增的应用上下文/工具历史折叠组件测试也先观察正文默认可见失败，再验证默认隐藏和主动展开后完整可读。最终 `npm test` 为 31 项通过，Chrome 为 10 项通过，最终源码类型检查、构建及清单校验通过。


## 真实工具运行后的历史快照更新

真实编辑验收发现：浏览器在工具尚未提交时刷新，历史首页会带读取时的“工具交互未完整提交”警告；任务完成后前端原来只更新运行投影，导致旧历史警告一直保留。本次增加同实例、同运行代次从 busy 到 idle 的一次性历史首页读取。

刷新按持久消息身份合并更新正文和当前首页警告，保留已经加载的更多历史及其稳定分页游标。仍使用较旧游标继续读取时，返回的提示标注为“旧分页快照”，不混同当前任务状态。历史首页刷新前后保存可见消息在阅读区的相对位置，避免警告或正文变化移动阅读锚点；按请求代次丢弃晚到的旧首页。刷新失败有明确提示，可通过重新打开会话重试，不后台无限轮询。

新增合并测试先观察旧正文/警告未更新失败；Chrome 用例先观察 busy→idle 后旧警告仍存在失败。修复后确认首页恰好读取两次（首次加结束刷新），后续 idle 状态不再触发读取；已加载分页仍在，下一游标仍为原稳定快照游标，阅读锚点偏移小于 2 像素。第二项 Chrome 用例确认任务结束后的新历史不会被延迟的旧首页覆盖。

本轮最终验证：32 项单元/组件测试、12 项 Chrome 测试通过；类型检查、生产构建及清单校验通过，最终两次生产构建清单逐字节一致。
